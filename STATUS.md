# Status — QR Code Directions App

_Last updated: 23 September 2026. First version, written from a read of the
repo rather than from memory of the work — correct anything that looks wrong._

## What this is

A QR code per resort that lets a visitor look up their site number and get
directions from the entrance to it. One deployment serves multiple resorts.

Staff use an admin area to create a resort, capture where every site actually
is, and download that resort's QR code. A visitor scans it, lands on
`/r/{resort-slug}`, types their site number, and sees the way there on the
resort's master plan.

## Where it runs

| | |
|---|---|
| Hosting | Vercel (see `vercel.json`) |
| Database | Supabase Postgres with PostGIS |
| Framework | Next.js (App Router) |
| Admin access | Email and password, allow-listed by email address |

Setup steps are in `README.md`. Migrations live in `supabase/migrations/`,
currently through `0017_diagnostics_switch.sql`.

## Where we're up to

**Phase 1 is built and working.** A visitor can scan, search a site number, and
see a straight-line distance and bearing from the entrance drawn on the resort's
master plan. "Follow me as I go" recomputes from the visitor's real position as
they drive, with the distance counting down.

The heavy lifting so far has gone into capturing site coordinates without anyone
walking a whole resort. There are four ways in: importing a scaled master plan
PDF and calibrating it against satellite imagery to compute every site at once,
clicking sites onto aerial imagery one at a time, dropping GPS pins while
standing on site, and CSV import. The satellite tool shows already-captured
sites as pins, so a resort under construction can be picked up again months
later without losing track.

Work is active — pull requests were merging as recently as 23 September.

## Open items

- [ ] **Phase 2: real routing.** Straight line and bearing is deliberately
  approximate. The plan is an admin tool to digitise each resort's road network
  — place intersections, connect them into paths, snap each site to the network
  — behind a `pgr_dijkstra` routing endpoint that returns a routed path and a
  walk-time estimate. Holding the road graph in our own database is the point:
  private resort layouts never need publishing to OpenStreetMap.
- [ ] **Phase 3:** PWA installability, offline queueing for the GPS capture
  tool, support for resorts with more than one entrance.
- [ ] **Turn-by-turn directions** — spoken and written manoeuvres. Needs street
  names on `graph_edges`, which nothing captures yet; the master plans carry
  them, so it is per-resort data entry. Deliberately parked until live
  directions have been watched in real use: these drives are 200–600 m, and the
  moving dot may turn out to be enough on its own.

## Gotchas

- **This is not the Next.js you remember.** Breaking changes from what most
  training data covers. The docs ship with the package at
  `node_modules/next/dist/docs/` — read the relevant page before writing code.
  `AGENTS.md` carries this rule and is regenerated by `next dev`, so committing
  it with your work is correct rather than something to strip out.
- **Visitors never see aerial imagery** — they see the resort's master plan.
  That is a deliberate decision, not an oversight. `README.md` explains the
  reasoning; don't "fix" it.
- **Live directions cost a location permission and hold a wake lock**, so it is
  opt-in. Anything that makes it automatic changes that bargain.
- **Straight-line distance is a known limitation, not a bug.** It understates
  the real drive on any resort whose roads curve. Phase 2 is the fix.
- **Site coordinates are the expensive part of onboarding a resort.** Before
  building anything new here, check whether it makes capture faster — that has
  been the binding constraint so far.
